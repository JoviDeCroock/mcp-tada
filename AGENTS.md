Read README.md and docs/ before starting work. `docs/` is contributor reference: architecture, the type-level mapper's schema decisions, CLI behaviour, and the server survey. README.md is what users read; a user-facing change is not finished until README.md covers it.
`.claude/skills/` holds task-scoped skills for this repo: `mcp-tada-snapshots` (regenerating and reviewing the committed `introspection.d.ts` files, and reading a `check` report), `mcp-tada-type-mapper` (changing `src/schema.ts` or any derived type, and the instantiation budget), `mcp-tada-cli` (adding a command or flag, and the `mcp-tada/cli` parity rule), and `mcp-tada-integration` (wiring the library into a project, for when you write or review an example). They expand on the rules below; this file stays the source of truth when the two disagree.
The core promise is zero runtime: `packages/mcp-tada/src/index.ts` may only forward to the SDK client, and `packages/mcp-tada/src/schema.ts` must stay a small purpose-built type-level mapper with no type-level library dependency. Any change to the mapper must keep `pnpm typecheck --extendedDiagnostics` instantiations in the tens of thousands, not millions, and must add a case to `packages/mcp-tada/test/schema.test-d.ts`.
The generated `introspection.d.ts` format (name-keyed tool map as a strict JSON type literal) is a public contract shared by `src/cli/introspect.ts`, `src/cli/snapshot.ts`, and `src/index.ts` in `packages/mcp-tada`, and by `packages/mcp-tada-server`. Change all three together and add a fixture.
This is a pnpm workspace: `packages/mcp-tada` is the client and CLI, `packages/mcp-tada-server` is the server-side helper, `e2e` runs the suite against real public servers (`pnpm test:e2e`, network required, not part of `verify`; its committed snapshots regenerate with `pnpm --filter @mcp-tada/e2e introspect`), and `examples/notes` is a runnable end-to-end example whose snapshot is committed; regenerate it with `pnpm --filter @mcp-tada/example-notes introspect` when the example server changes. When making changes that affect a published package, create a changeset (.changeset/<name>.md) describing the change. Use patch/minor/major as appropriate. Normally use one direct sentence stating the user-visible outcome. Add a second sentence only when an important behaviour needs clarification; add a short migration note or example only for a breaking change. A changeset becomes a CHANGELOG entry, not a miniature PR description: never narrate the implementation, investigation, tests, edge cases, rationale, benchmarks, alternatives, or review history. If it needs headings, bullets, or multiple paragraphs, it is too long.
A husky pre-commit hook runs lint-staged (oxfmt and oxlint on staged files) and then `pnpm run verify --check`; do not bypass it with `--no-verify`. Before committing, always run `pnpm run verify`. It formats and lints, then runs build, typecheck, and the unit tests in parallel, and prints output only for failing steps. Pass `--check` to report formatting and lint instead of rewriting files.
When creating a pull request, always follow .github/PULL_REQUEST_TEMPLATE.md and fill any non-applicable sections with N/A.
